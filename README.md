# EGGROLL Hyperscale ES with vLLM

[![Paper](https://img.shields.io/badge/paper-A42C25?style=for-the-badge&logo=arxiv&logoColor=white)](https://arxiv.org/abs/2511.16652)

This repo contains the official code for the transformer LLM experiments in the paper [Evolution Strategies at the Hyperscale](https://arxiv.org/abs/2511.16652). 

## Code:

The main script is `es_lora_multinode.py`. This is an almost single file implementation, apart from the tasks which are in `tasks.py`.

`es_lora_multinode_moe.py` is the updated version that supports **Mixture-of-Experts (MoE)** models with Tensor Parallelism and Multi-LoRA (requires vLLM >= 0.16.0). It is backward compatible with `es_lora_multinode.py`.


## Tasks:

- `math:gsm8k`, `math:asdiv2k`, `math:math12k`, `math:orz57k`, `math:deepscaler40k`: Math questions. These tasks trigger automatic evaluation on `["math", "amc", "olympiad_bench", "minerva", "aime24"]`.
- `zeros`: For debugging. Task is to output all zeros.
- `random`, `random-boxed`:  For exploring behaviour with pass@k objective. Aim is to guess a random number. Options without and with requiring `\\boxed{}` formatting.
- `countdown`: Questions in countdown.json from https://github.com/VsonicV/es-fine-tuning-paper.


## Installation:

Ensure paths set in bashrc:

```bash
export PATH=/usr/local/cuda/bin${PATH:+:${PATH}}
export LD_LIBRARY_PATH=/usr/local/cuda/lib64${LD_LIBRARY_PATH:+:${LD_LIBRARY_PATH}}
```

Then install `vllm, tyro, wandb, weave, peft, datasets, gem-llm, pylatexenc`, e.g. with:
```bash
cd $SCRATCH && mkdir uv_envs && cd uv_envs && mkdir vllm_env
cd $SCRATCH/uv_envs/vllm_env
uv venv --seed -p=3.12
source $SCRATCH/uv_envs/vllm_env/.venv/bin/activate
# To support MoE + TP + Multi-LoRA, use vLLM 0.16.0 or later
srun --gpus 1 uv pip install vllm==0.17.0 --torch-backend=auto
uv pip install tyro wandb weave peft datasets gem-llm pylatexenc
```

We provide a `requirements.txt` containing the version info used for these experiments.

Before running, dowload model to cache, e.g. with:

```bash
source $SCRATCH/uv_envs/vllm_env/.venv/bin/activate
srun --pty bash
python
from transformers import AutoModelForCausalLM, AutoTokenizer
model_name = "Qwen/Qwen3-8B"
model, tokenizer = AutoModelForCausalLM.from_pretrained(model_name), AutoTokenizer.from_pretrained(model_name)
```


## Launching jobs:

Use `sbatch slurm_launch_multinode_n1.sh` and `sbatch slurm_launch_multinode_n16.sh` launch jobs on 1 and 16 nodes of 4 gpus respectively. Hyperparameters can be changed within the bash launch scripts.

## Docker

A docker image running EGGROLL for training can be generated by running `docker_launch_base_g1.sh`. This script creates necessary directories (for logs, wandb, HF, etc...), and produces a script `run_inside_docker.sh` containing the parameters for training (which can be set from `docker_launch_base_g1.sh`). It then builds a docker container & runs the corresponding image.

# Replicating h1 (GSM-LongHorizon) with EGGROLL

This section documents how to replicate the [h1](https://github.com/AlesyaIvanova/h1)
long-horizon reasoning run (Qwen2.5-3B-Instruct on GSM-LongHorizon, stage-wise
curriculum over horizon lengths 1–5) with **EGGROLL replacing DrGRPO**. Same
model, dataset splits, prompts, rewards, curriculum and evaluation — only the
optimiser changes.

### Files added for this replication

| File | Purpose |
| --- | --- |
| `h1_math_utils.py` | **Verbatim** copy of `h1/math_utils.py` (`grade_answer` etc.), used as the answer comparator for the correctness reward. |
| `h1_rewards.py` | h1's reward + answer-extraction functions (verbatim from `h1/grpo.py`) plus thin adapters that score a single response and sum them into a scalar fitness. |
| `h1_gsm_eval.py` | **Vendored** copy of h1's `gsm_eval.py` (the between-stage checkpoint selector), so a clone of this repo is self-contained. Only change vs upstream: `enable_thinking=False` for Qwen3 (see below). |
| `tasks.py` → `GSMLongHorizonTask` | New task: h1's prompts + h1's total DrGRPO reward as EGGROLL fitness. |
| `run_h1_curriculum.sh` | Curriculum runner: trains + merges one stage per invocation, then pauses for external checkpoint selection. |
| `run_h1_smoke.sh` | Tiny end-to-end debug run (pop 8, 4 iters, 32-question subset) to validate the whole stack in minutes before a real run. |
| `slurm_launch_gsm_longhorizon.sh` | Slurm launch script with the experiment config block (per-stage completion lengths, EGGROLL hyperparameters, equal-compute reference). |

### The task and its reward

`GSMLongHorizonTask` (task spec `gsm_longhorizon:<int|float>:<path>`):

* **Prompts** are built identically to h1's `grpo.py`: a chat template with a
  system message containing h1's exact `SYSTEM_PROMPT` (`<reasoning>…</reasoning>
  <answer>…</answer>`) and a user message with the question.
* **Fitness** is h1's DrGRPO **total reward** per rollout = correctness
  + `xmlcount` + `soft_format` + `strict_format` + numeric-format reward, where
  the numeric-format reward is `int_reward_func` (horizon 1) or `float_reward_func`
  (horizons 2–5). This mirrors h1's `--float_reward_func` flag via the `int`/`float`
  token in the task spec. Correctness (2.0) uses h1's extractor
  (`extract_answer_from_text`) with the vendored `h1_math_utils.grade_answer`
  comparator.
* **Per-question normalisation is preserved.** Fitness is a scalar per rollout;
  the ES loop then centres fitnesses **per prompt/question column**
  (`fitness_per_prompt` in `es_lora_multinode.py`), i.e. each question's
  population fitnesses are baselined against that question's mean — the ES analog
  of GRPO's per-group baseline, **not** a global z-score across the mixed batch.

### 1. Download and split the GSM-LongHorizon dataset

(From h1's README — produces `train_len_{1..5}.jsonl` and `test_len_{1..5}.jsonl`.)

```bash
huggingface-cli download alesiaivanova/GSM-LongHorizon --repo-type dataset --local-dir ./GSM-LongHorizon

python -c "import pandas as pd; pd.read_parquet('GSM-LongHorizon/data/train-00000-of-00001.parquet').to_json('GSM-LongHorizon/train.jsonl', orient='records', lines=True)"
python -c "import pandas as pd; pd.read_parquet('GSM-LongHorizon/data/test-00000-of-00001.parquet').to_json('GSM-LongHorizon/test.jsonl', orient='records', lines=True)"

# Split by horizon length (train + test, horizons 1..5)
for n in 1 2 3 4 5; do
  python -c "import json,sys; n=int(sys.argv[1]); data=[json.loads(l) for l in open('GSM-LongHorizon/train.jsonl')]; open(f'GSM-LongHorizon/train_len_{n}.jsonl','w').writelines(json.dumps(x)+'\n' for x in data if x['horizon_length']==n)" $n
  python -c "import json,sys; n=int(sys.argv[1]); data=[json.loads(l) for l in open('GSM-LongHorizon/test.jsonl')];  open(f'GSM-LongHorizon/test_len_{n}.jsonl','w').writelines(json.dumps(x)+'\n' for x in data if x['horizon_length']==n)" $n
done
```

Each JSONL row has `question`, `final_answer`, `horizon_length` (the same fields
h1 reads). Also make sure the base model is cached (the launch scripts set
`HF_HUB_OFFLINE=1`):

```bash
python -c "from transformers import AutoModelForCausalLM, AutoTokenizer; m='Qwen/Qwen2.5-3B-Instruct'; AutoModelForCausalLM.from_pretrained(m); AutoTokenizer.from_pretrained(m)"
```

### Running on Qwen3 (e.g. `Qwen/Qwen3-1.7B`)

Everything works with any HF causal LM; just set the model. A smaller model like
`Qwen/Qwen3-1.7B` is a good choice for a first debug/eval run (fits comfortably
on one A100, faster iterations). One Qwen3-specific gotcha is handled for you:
Qwen3's chat template defaults to **thinking mode** (`enable_thinking=True`),
which emits `<think>…</think>` and both breaks h1's `<reasoning>/<answer>`
format rewards and blows the token budget. `GSMLongHorizonTask` and
`h1_gsm_eval.py` both pass `enable_thinking=False`, so training and eval use the
same non-thinking format (this is a no-op on Qwen2.5). Nothing else changes:

```bash
# cache the model once
python -c "from transformers import AutoModelForCausalLM, AutoTokenizer; m='Qwen/Qwen3-1.7B'; AutoModelForCausalLM.from_pretrained(m); AutoTokenizer.from_pretrained(m)"
```

### Quick smoke test (do this before any real run)

`run_h1_smoke.sh` runs the **entire** pipeline at minimal size — prompt build →
vLLM multi-LoRA generation → h1 reward/fitness → EGGROLL ES update → checkpoint
→ merge → `gsm_eval` — in a few minutes. The numbers it prints are meaningless;
it exists to confirm nothing throws on your GPU/driver/vLLM stack before you
spend hours on a real run. It only needs `train_len_1.jsonl` / `test_len_1.jsonl`.

```bash
CUDA_VISIBLE_DEVICES=0 ./run_h1_smoke.sh                 # defaults to Qwen/Qwen3-1.7B
# or point it at the real model:
MODEL=Qwen/Qwen2.5-3B-Instruct ./run_h1_smoke.sh
```

Tunables (all env-overridable): `MODEL`, `POPULATION_SIZE` (default 8, even),
`PROMPT_BATCH_SIZE` (2), `NUM_ITERATIONS` (4), `MAX_TOKENS` (256),
`SUB_DATASET_SIZE` (32), `EVAL_SAMPLES` (8).

### 2. The curriculum

| Stage | Split | `max_completion_length` (`--max-tokens`) | Reward mode |
| --- | --- | --- | --- |
| 1 | `train_len_1.jsonl` | 768  | `int`   |
| 2 | `train_len_2.jsonl` | 1024 | `float` |
| 3 | `train_len_3.jsonl` | 1280 | `float` |
| 4 | `train_len_4.jsonl` | 1536 | `float` |
| 5 | `train_len_5.jsonl` | 1536 | `float` |

Max prompt length is 512 throughout in h1 (see *Deviations* — eggroll-vllm does
not truncate prompts). Each stage is trained from the **merged** best checkpoint
of the previous stage.

**Single-node / interactive (`run_h1_curriculum.sh`)** — trains + merges one
stage, then prints the exact `gsm_eval.py` commands and pauses:

```bash
# Stage 1 (base = Qwen/Qwen2.5-3B-Instruct)
STAGE=1 ./run_h1_curriculum.sh
# ... run the printed gsm_eval.py commands, pick the best merged step ...
# Stage 2 (base = chosen merged HF dir from stage 1)
STAGE=2 BASE_MODEL=runs/h1_curriculum/stage1_len1/merged/step_250 ./run_h1_curriculum.sh
# ... repeat for stages 3, 4, 5, each time passing the previous stage's best merged dir ...
```

**Slurm (`slurm_launch_gsm_longhorizon.sh`)** — one stage per job:

```bash
STAGE=1 sbatch slurm_launch_gsm_longhorizon.sh
STAGE=2 BASE_MODEL=runs/h1_curriculum/stage1_len1/merged/step_250 sbatch slurm_launch_gsm_longhorizon.sh
```

### 3. Between stages: merge + external checkpoint selection

EGGROLL checkpoints are fused vLLM weights, not HF models, so they must be
merged before evaluation or reuse. `run_h1_curriculum.sh` merges every saved
checkpoint of a stage to `…/stageN_lenH/merged/step_<N>` (via
`merge_checkpoint.py --output-dir`). Then, exactly as h1 recommends, evaluate the
merged checkpoints on horizons 1–3 and pick the overall best:

```bash
for step in 50 100 150 200 250 299; do
  python h1_gsm_eval.py \
    --models runs/h1_curriculum/stage1_len1/merged/step_${step} \
    --datasets GSM-LongHorizon/test_len_1.jsonl GSM-LongHorizon/test_len_2.jsonl GSM-LongHorizon/test_len_3.jsonl \
    --instruct --tp 1 \
    --out_file runs/h1_curriculum/stage1_len1/merged/eval_step_${step}.json
done
```

Use the best `…/merged/step_<BEST>` directory as `BASE_MODEL` for the next stage.
Selection is intentionally **manual** (the runner pauses); nothing is auto-selected.

### 4. Hyperparameters and equal-compute budget

The EGGROLL hyperparameters (`population_size`, `sigma`, `learning_rate`,
`lora_r`, …) default to the repo's existing math ES run
(`slurm_launch_base_n1.sh`, `math:deepscaler40k`) and are **not tuned for
GSM-LongHorizon — treat them as a starting point.** See the config block in
`slurm_launch_gsm_longhorizon.sh` / `run_h1_curriculum.sh`.

**Equal-compute reference (per stage):**

* h1 GRPO: `300 steps × (per_device_bs 1 · grad_accum 16 · num_gpus) prompts ×
  num_generations 16`. On 1 GPU: `300 × 16 × 16 = 76,800` rollouts/stage
  (scales with `num_gpus`).
* EGGROLL: `NUM_ITERATIONS × POPULATION_SIZE × PROMPT_BATCH_SIZE ×
  SAMPLES_PER_PROMPT`. With defaults `300 × 1024 × 16 × 1 = 4,915,200` ≈ **64×**
  h1's rollout budget.
* Budget-matched (~76,800 rollouts/stage, 300 iters, spp 1): set
  `POPULATION_SIZE × PROMPT_BATCH_SIZE ≈ 256` (e.g. `pop 256, pbs 1`). ES usually
  needs a larger population for a usable gradient estimate, so decide whether to
  compare at equal rollouts or at equal ES steps.

### Deviations from h1 forced by eggroll-vllm's structure

* **Exploration mechanism.** GRPO samples `num_generations` completions per
  prompt; EGGROLL explores via a *population* of LoRA-shaped weight perturbations
  evaluated on each prompt. There is no `num_generations`; the per-question
  "group" is the population. Generation is greedy (`temperature 0`) because
  diversity comes from the perturbations, not sampling.
* **Correctness comparator.** The requested `math_utils.grade_answer` is h1's
  comparator for the **MATH** benchmark (`math_eval.py`). h1's **GSM** eval
  (`gsm_eval.py`, the between-stage selector) actually extracts the `<answer>`
  number and compares floats with `abs(pred − gt) < 1e-2`; h1's GRPO *training*
  reward uses `< 1e-9`. We vendor `math_utils.py` verbatim and use `grade_answer`
  for the training correctness term (as instructed). For the pure-numeric
  GSM-LongHorizon answers these agree except in rare tolerance-boundary cases.
* **Prompt-length cap.** h1 truncates prompts to `max_prompt_length=512` (TRL).
  eggroll-vllm passes the full chat-templated prompt to vLLM (no truncation), so
  512 is documented only. GSM-LongHorizon prompts generally fit.
* **Truncated completions.** h1/DrGRPO scores truncated completions normally;
  `GSMLongHorizonTask` does the same (it does **not** zero them the way the
  existing `MathTask` does).
* **Checkpoints need merging.** EGGROLL saves fused vLLM weights
  (`model_weights.safetensors`), not HF checkpoints, so an explicit
  `merge_checkpoint.py` step is required before `gsm_eval.py` or before reuse as
  the next stage's base model.
* **Dataset order.** h1's `grpo.py` defaults to `shuffle_dataset=False`;
  `GSMLongHorizonTask` matches that (`shuffle=False`), unlike `MathTask` which
  shuffles.
* **Repairs to run at all (additive).** `tasks.py` imported a since-deleted
  `egg_img.py` and `merge_checkpoint.py` imported since-deleted
  `DrawEggTask/DrawChickTask`; both broke `import tasks` (and thus the trainer).
  These dangling imports are now guarded (unused symbols). `merge_checkpoint.py`
  also gained an optional `--output-dir` (its default output path was hard-coded
  to the original author's cluster tmp dir). Core ES update, noiser and existing
  tasks are unchanged.
